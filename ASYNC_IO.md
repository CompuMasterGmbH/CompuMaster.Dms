`BaseDmsProvider` now exposes Task-based counterparts for remote listing, existence checks, lookup, upload, download, copy, move, deletion, folder and collection creation, authorization, sharing, links, and visible users/groups. `DmsFactory` also offers asynchronous provider authorization. Path and identity-preserving item overloads remain distinct. Purely local path helpers, configuration properties, and credentials-object construction stay synchronous. Where a provider has native async primitives, the common read helpers compose them. Other operations use the serialized worker fallback. This keeps UI callers responsive while preserving the existing synchronous API.

The fallback gate is process-wide per provider backend and covers calls made through these Task-based fallback methods, including the legacy asynchronous copy hooks. Waiting calls can be canceled; an active synchronous request cannot. Calls made directly through the synchronous API, other processes, and external client-library calls are outside this gate. It therefore mitigates parallel `Task.Run` failures reported in [upstream issue #8](https://github.com/CompuMasterGmbH/CompuMaster.CenterDevice.IO/issues/8) only for callers using the new API. `ConfigureAwait(False)` controls continuation context but does not move a synchronous HTTP call off the UI thread; the single central `Task.Run` is intentional until the CenterDevice client exposes native async I/O. That client also needs a limiter covering all transport calls.

## Browser busy state and provider concurrency

The browser busy state guards one logical operation in the active form, preventing duplicate submissions and conflicting selection or mutation actions while remote work is pending. It is independent of the shared provider semaphore: multiple forms and non-UI consumers still share the provider allowance. CenterDevice and Teamwork fallback operations each permit one active worker per backend in this process. WebDAV, ownCloud, and Nextcloud use the shared per-origin HTTP allowance of two active requests. These defaults are conservative and are not verified server limits.

Tree expansion cancels the immediate WinForms expansion event, awaits the child listing, and then expands the loaded node. Repeated loads of the same node share one pending task, known-empty nodes require no child request, and failed loads retain their placeholder for retry. Programmatic navigation suppresses duplicate selection refreshes. File listing ignores superseded responses, and sorting uses the already loaded file list without another request. Folder creation and deletion preserve child metadata and item identity; file deletion batches await each item. Copy/move refresh also runs after a partially completed operation while preserving its original failure.

Sharing dialogs await user/group listing, current-user lookup, share mutations, link creation/update/deletion, and link-detail refresh. Their busy guard covers the complete server operation and model update, rejects duplicate actions, and prevents closing the dialog while a request is active. Browser sharing-icon refresh waits for other browser work and updates the affected item. Hidden sharing rows remain visible without being treated as selectable identifiers. `DmsLink.RefreshAsync` and `BaseDmsProvider.RefreshLinkAsync` use the serialized fallback for existing synchronous detail callbacks; successful refresh marks details initialized so later property reads do not immediately repeat the request on the UI thread. Providers can override the asynchronous refresh path.

Property dialogs await link details and referenced folder/collection names before formatting local data. A failed optional reference lookup retains its identifier and does not hide the remaining properties. The profile-only browser constructor defers authorization to asynchronous form startup. The public synchronous `DmsProvider` getter and the constructor accepting an explicit `RemoteInstanceSelector` retain their existing synchronous contracts. Existing instance discovery/selection remains synchronous for compatibility with external implementations.

## Published limits and applicability

The [Scopevisio API overview](https://help.scopevisio.com/en/collections/1118607-api) and [OpenScope REST reference](https://appload.scopevisio.com/static/swagger/index.html) did not establish a numeric concurrency ceiling, request rate, or account/tenant/IP scope. [Scopevisio's general documentation](https://help.scopevisio.com/en/articles/467359-general-documentation) directs Teamwork clients to the CenterDevice API contract, replacing its base URL and authentication token. This does not establish identical operational quotas for OpenScope authorization, the Teamwork bridge, and direct CenterDevice. No authenticated response headers or backend boundary measurements were collected.

The public CenterDevice viewer required JavaScript; its visible download now provides [Public REST API 2.29](https://public.centerdevice.de/download/02bf3cfd-06c6-4d43-9cd4-3c18aab0020a.9929daf5-2ef4-4094-80e9-d3147e0d41fd), dated September 10, 2025, reviewed October 6, 2026 (SHA-256 `5edf3d5d916e82b60527a9e5c8e5bd1f01a836d3c6a526dcf631414f94fc00d6`). Section 4.1.6, page 27, specifies HTTP 429 and Retry-After seconds with dynamic thresholds and delays; waiting does not guarantee acceptance. Section B.1, page 288, defines HTTP 400/code107 with a 64-bit byte limit and code108 for size mismatch. Sections 5.7.1-5.7.4, pages 155-159, define configurable upload-link defaults: one week, 50 uploads, and 2 GiB total. Max-bytes must be positive and divisible by 1 GiB. These link settings are not a universal document-upload ceiling; no fixed direct-upload byte ceiling was established.

The [CenterDevice product description](https://www.centerdevice.de/leistungsbeschreibung/) advertises files up to 10 GB. The [Scopevisio Weblogin guide](https://help.scopevisio.com/en/articles/467345-weblogin-teamwork) describes upload-link settings. Neither proves a universal direct REST upload limit for the configured Scopevisio account. The shared DMS API therefore does not impose these values as provider-independent limits; validate applicable server responses and preserve their original causes.

HTTP [429](https://www.rfc-editor.org/info/rfc6585/) can include `Retry-After`; [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3) defines its seconds and HTTP-date forms. These are general HTTP rules, not evidence that either DMS backend issues a particular status or applies a particular quota.

The WebDAV transport therefore uses a conservative per-origin, process-wide allowance of **2 concurrent requests** and **30 starts per rolling minute**. These are local safety defaults, not vendor limits. Different processes still require coordination if they share a constrained account. A streaming response holds its concurrency slot until its body is consumed or disposed. Cancellation works while waiting for either allowance. Read requests (`GET`, `HEAD`, `PROPFIND`) may be retried at most three times for 408, 429, 500, 502, 503, and 504, or a transport `HttpRequestException`. Further attempts stop when 30 seconds have elapsed since the initial attempt; the first request and writes are not shortened by this retry budget. `Retry-After` takes precedence over exponential backoff with jitter. A response is returned intact when the next retry delay would exceed the budget. Writes (`PUT`, `POST`, `MKCOL`, `COPY`, `MOVE`, `DELETE`) are not replayed because an ambiguous timeout could duplicate or reorder a change. Authentication and validation errors are not retried.
